# GAME OVER·CONTINUE·NEW GAME (7-B)

## 1. 판정은 로직(정산 순간), 표시는 화면(연출 뒤)
- **선택:** `GameState.settle_spin()` 맨 끝에서 크레딧이 0이면 `game_over` 시그널을 보낸다. 화면은 받아서 정산·피버·풀 연출이 모두 끝난 뒤 `gameover_delay_sec` 뒤에 띄운다.
- **이유:** 결과는 START 순간에 정해지고 연출은 보여주기만 한다는 원칙을 지킨다. 정산 연출 중에도 로직 크레딧은 이미 최종값이라 판정이 흔들리지 않는다. GAME OVER가 되는 판은 항상 당첨 0이라 연출이 겹치는 일은 구조상 없고, 그래도 표시 조건에 연출 여부를 넣었다.
- **다른 후보:** 크레딧이 바뀔 때마다 상태를 감시(기존 테스트가 크레딧을 직접 0으로 놓는 곳이 많아 엉뚱한 곳에서 GAME OVER가 뜸), 화면에서 판정(로직 단독 테스트 불가).

## 2. GAME OVER는 "크레딧 0 + 진행 중인 판 없음"과 항상 일치
- **선택:** `grant_credit()`이 크레딧을 0보다 크게 만들면 GAME OVER 플래그를 해제한다. `insert_coin()`은 GAME OVER 중에도 막지 않고 `coin_allowed()`만 따른다. 입력 잠금은 화면(오버레이)이 맡고, 화면은 로직이 GAME OVER가 아니게 되면 스스로 닫는다.
- **이유:** 처음에는 로직에서 GAME OVER 중 COIN을 막았다가 기존 테스트(크레딧이 0이 된 뒤 COIN으로 이어 가는 루프)가 끝나지 않는 것을 발견했다. 막는 규칙은 승인 계획에 없던 것이라 사용자 결정(A안)으로 풀었다.
- **다른 후보(B안):** 로직에서 막고 기존 테스트를 고치기. 테스트를 규칙에 맞춰 바꾸는 일이라 채택하지 않았다.

## 3. 크레딧이 올라가는 길은 `grant_credit` 하나
- **선택:** 시작 지급·CONTINUE·개발용 COIN이 모두 `grant_credit(amount, reason)`을 거친다(이유 `start` / `continue` / `test_coin`, 시그널 `credit_granted`). 당첨금은 정산 경로라서 거치지 않는다.
- **이유:** 최고 기록·통계에서 "테스트 판"을 제외하는 표시(`run_tainted`)를 한 곳에서 남기고, 7-C 시작 화면의 START가 같은 입구를 쓰게 한다.
- **NEW GAME 코인:** 별도 키 없이 `start_credit`을 따른다. START와 NEW GAME이 같은 `new_game()`을 쓰므로 값도 하나가 어긋날 일이 없다.

## 4. 값은 `economy.json`
- **선택:** `start_credit`(3,000) / `continue_credit`(1,000) / `continue_max`(3) / `coin_amount`(100)을 `data/economy.json`에 둔다. `balance.json`으로 옮기지 않는다.
- **이유:** 기존 로더·테스트·결정 기록(2026-11-08-gamestate-economy)이 있고 로직(SlotLogic)을 건드리지 않는다. 시작 크레딧은 F5로 해 보고 사용자가 직접 조정한다(코드 하드코딩 금지). 테스트도 현재 값에 묶이지 않고 economy 값에서 기대값을 계산한다.
- **다른 후보:** `balance.json`으로 이동(economy.json 삭제와 테스트 호출부 약 30곳 수정이 따라와 제외).
- **소진 속도:** 시작 3,000 + CONTINUE 1,000×3일 때 최대 베팅(64)은 첫 GAME OVER까지 중앙값 117스핀이다. 피버·풀이 RTP의 약 30%p를 차지하는데 체리 피버가 평균 186스핀, 풀이 3,277스핀에 한 번이라 대부분 받기 전에 끝나서 단순 계산(약 655스핀)보다 짧다. 사용자가 의도한 값으로 확정했다.

## 5. COIN은 `coin_allowed()` 한 곳에서 판단
- **선택:** `coin_allowed()` = 개발 빌드(`OS.is_debug_build()`) and 테스트 모드 스위치. 릴리즈 빌드에서는 항상 false. 테스트가 릴리즈 상황을 흉내 낼 수 있게 두 값은 변수(`dev_build`, `test_mode`)다. 8-B 설정 화면은 `test_mode`만 연결하면 된다.
- **동작:** 불가하면 COIN 버튼은 자리 그대로 회색, C 키는 소리 없이 무시, 안내 문구는 "크레딧이 부족합니다."(가능하면 기존 "COIN(C)…" 문구).
- **확인 필요:** "디버그와 함께 내보내기"로 만든 exe가 `OS.is_debug_build()`에서 개발 빌드로 취급되는지는 실제 내보내기 때 확인한다.

## 6. BGM·소리
- **선택:** GAME OVER 동안 BGM을 `bgm_gameover_fade_sec`로 줄여 일시정지하고(`BgmPlayer.pause_music`), CONTINUE·NEW GAME 때 멈춘 자리부터 키운다(`resume_music`). 화면이 뜰 때 `gameover.wav`, 버튼이 받아들여지면 `button.wav`.
- **이유:** 메인→피버 전환과 같은 방식(위치 기억)이라 곡이 처음부터 다시 시작하지 않는다.

## 7. 최고 기록은 메모리 집계만
- **선택:** 한 판의 최고 크레딧·스핀 수·이어하기 사용 수·테스트 판 여부를 메모리에만 세고 저장하지 않는다. `user://` 저장은 8단계 설정 저장과 함께 설계한다.
- **이유:** 내보낸 exe는 `res://`에 쓸 수 없어 저장 구조가 어차피 필요하고, 8단계에서 한 번에 정하는 편이 낫다.
